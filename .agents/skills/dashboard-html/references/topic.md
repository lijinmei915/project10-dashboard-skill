# Dashboard Layout Reference

> 用途：提供一个轻量生成式 UI dashboard 在卡片、间距、布局和多端适配上的默认规范。

## 页面骨架

- 页面背景默认使用 `#f5f7fa`。
- 主内容区使用单一居中容器，`max-width: 1160px`。
- 页面左右内边距默认使用桌面端 `24px`、移动端 `16px`。
- 区块之间保持稳定纵向节奏，主 section 间距默认使用 `28px`。
- 页面应先为生成式 UI 的信息扫描服务，优先保证卡片组织和信息顺序清晰，再考虑装饰感。
- 即使用户要求调整布局组合，也默认保留 page header，不要轻易删除页面标题和上下文说明区。
- page header 默认仍应作为首个信息层，优先承载标题、辅助说明、状态或操作。
- 固定的是页面骨架和样式基线，不是固定某一套页面模块顺序。

## 默认视觉 Token

| Token | 默认值 |
|------|------|
| Page background | `#f5f7fa` |
| Card background | `#ffffff` |
| Card shadow | `0 2px 10px rgba(15,23,42,0.04)` |
| Card radius | `14px` |
| Card padding | `20px` |
| Dense card padding | `16px` |
| Accent | `#ff7a2f` |
| Accent soft | `rgba(255,122,47,0.12)` |
| Page max width | `1160px` |
| Desktop page padding | `24px` |
| Mobile page padding | `16px` |
| Section gap | `28px` |

## 深色模式

- 深色模式只替换颜色 token，不重置布局原语、圆角、间距或卡片层级。
- 默认深色 token：page background `#111827`、card background `#1f2937`、muted surface `#172033`、primary text `#f9fafb`、secondary text `#cbd5e1`。
- 深色卡片阴影使用 `0 2px 10px rgba(0,0,0,0.22)`；保持同一阴影尺度，不改成厚重悬浮效果。
- 用户要求深色界面时，将初始 `data-theme` 设为 `dark`；主题由对话确定，不生成页面内切换控件。
- `data-theme` 只是选择器；深色输出必须保留完整的 `html[data-theme="dark"]` token 覆盖和 `color-scheme: dark`，不能只改属性或 `:root`。
- 用户只要求切换主题时，只替换颜色 token（必要时阴影 token）；字号、行高、间距、布局、尺寸、圆角和结构保持不变，不自行做可读性优化。

## 主题色

- 默认主题色为橙色：`--accent: #ff7a2f`、`--accent-soft: rgba(255,122,47,0.12)`。
- 用户可给出任意明确的 CSS 色值，或明确的中文 / 英文颜色名称；将非 CSS 名称转换为具体 CSS 色值后再写入页面。蓝色、绿色、黄色、橙色、黑色只是常见示例，不是可选范围。
- 对应的 `--accent-soft` 默认使用同色 `12%` 透明度；明确 CSS 色值可写为 `color-mix(in srgb, <color> 12%, transparent)`。
- 自定义主题色只覆盖 `--accent` 和 `--accent-soft`，用于选中态、中性标签和非语义强调；不要替换成功、提醒、错误等状态色。
- 自定义覆盖要放在 `:root` 和 `html[data-theme="dark"]` token 块之后，并使用 `html[data-theme]` 选择器，保证深色模式也能保持用户指定的主题色。

## 卡片样式

- 卡片背景、圆角、阴影和内边距默认使用上面的 token 表。
- 卡片默认不加描边；只有层次明显不够时，才考虑使用 `1px solid rgba(15,23,42,0.04)`。
- `starter.html` 里的占位框只用于提示可替换区域；真实内容生成后，不应保留这些可见占位外框。
- 用户若只要求“换布局”，默认只调整布局原语组合，不重置卡片阴影、圆角、背景和留白基线。
- 用户若未明确要求改视觉，默认保留 `starter.html` 里既有的样式系统，只调整占位和布局内容。
- 若保留样式 token 机制，优先沿用 `starter.html` 中的 token 名和值，不额外发明新的卡片阴影 token。

## 布局规则

推荐把布局理解为以下 6 个通用原语，而不是具体组件：

- `surface`：单个独立面板或卡片容器。
- `stack`：纵向堆叠区域，适合多个小面板连续排列。
- `grid`：等宽网格区域，适合摘要块、卡片阵列或任意重复结构。
- `split`：非等宽分栏区域，适合主内容和辅助内容并列，但列宽应可调，不要写死。
- `canvas`：大面积承载区，适合图表、白板、地图、媒体、复杂自定义内容。
- `table-area`：结构化数据区，适合表格或行列型信息，但不限制具体业务内容。

## 容器语义

| 类型 | 用途 | 规则 |
|------|------|------|
| `surface` | 真实信息卡片或独立面板 | 使用 Card token，默认无外描边 |
| `content-area` | 图表、列表、媒体等真实内容承载区 | 落在 `surface` 内，不保留 placeholder 外框 |
| `placeholder` | starter 的空状态提示 | 仅无真实内容时显示；填充真实内容后移除 |

`content-area` 和 `placeholder` 是内容状态，不是新增布局原语。

不要把当前 starter 理解成固定模板：

- 它提供的是样式基线和页面骨架，不是固定模块清单。
- 不要求页面一定出现 KPI 卡片、4 列摘要区或当前所有 section。
- 允许根据内容需要使用 2 列、3 列或 4 列 `grid`。
- 允许只使用其中一部分原语组合，而不是每次都把所有原语都用上。

## 组合原则

不需要穷举所有布局变体，更适合定义“原语如何组合”：

- `surface` 是基础承载单元，其他原语通常都落在某个 `surface` 内，或本身作为独立 `surface` 出现。
- `grid` 适合重复结构，默认建议 2-4 列，桌面端列间距建议 `16px-20px`，但列数应允许按内容调整。
- `split` 适合主辅分栏，默认可使用类似 `2fr / 1fr` 的关系，但不应把双栏结构视为固定模板。
- `stack` 适合右侧说明区、辅助区、连续列表区或任意纵向内容流。
- `canvas` 通常出现在较大的 `surface` 内，作为主要内容承载区。
- `table-area` 通常作为独立 `surface` 出现，用于结构化信息展示。
- `stack`、`grid`、`split` 都应能在移动端堆叠成单列。
- 表格、长列表、说明块和自定义模块都应作为独立 `surface` 出现，不要混成无层级的大块。
- 同一 section 内若有标题和操作按钮，优先采用横向 header：左标题右操作。

## 选用规则

为避免原语互相打架，优先按“内容结构”而不是“视觉名字”选用：

### `surface`

- 任何独立卡片或面板都先视为 `surface`
- 如果某块内容已经可以单独命名、单独留白、单独移动，它通常就是一个 `surface`
- `surface` 是基础承载单元，不与其他原语竞争

### `grid`

- 需要并列展示多个重复结构时优先使用 `grid`
- 适合摘要卡、并列信息块、重复模块阵列
- 如果核心问题是“横向比较多个同级单元”，优先 `grid`
- 如果不是重复结构，而是主辅关系，不要误用 `grid`，应改用 `split`

### `split`

- 需要主内容和辅助内容并列时优先使用 `split`
- 适合“左主右辅”或“主区 + 侧栏”结构
- 如果两侧内容不是同级，而是明显主次分工，不要用等宽 `grid`，应优先 `split`
- 如果分栏过多或每栏过窄，应减少分栏并在窄屏下堆叠

### `stack`

- 需要纵向连续内容流时优先使用 `stack`
- 适合短信息块、说明块、状态块、事件块、过滤块、操作块
- `stack item` 默认全宽排列、间距稳定、允许高度自适应
- 在窄屏下保持单列，不切成多列，不写死固定高度
- 如果单个 `stack item` 已经变成复杂复合区域，应升级成独立 `surface`

### `canvas`

- 需要大面积承载区时优先使用 `canvas`
- 适合图表、媒体、地图、复杂图形、自定义嵌入内容
- `canvas` 不单独承担页面结构角色，通常作为 `surface` 内部的主内容区
- 如果只是普通说明块或短列表，不要误用 `canvas`

### `table-area`

- 需要行列型、字段型、结构化明细时优先使用 `table-area`
- 适合表格、记录列表、明细区、可扫描数据区
- `table-area` 通常作为独立 `surface` 存在
- 如果信息重点是浏览大块内容而不是扫描字段，不要误用 `table-area`

## 冲突消解

当多个原语都像是可选项时，按以下优先级判断：

- 先判断是否为独立卡片：是，则外层先落成 `surface`
- 再判断内部是重复并列、主辅分栏、纵向流、重内容承载还是结构化明细
- 重复并列选 `grid`
- 主辅分工选 `split`
- 纵向连续小块选 `stack`
- 大面积承载区选 `canvas`
- 行列扫描型内容选 `table-area`

## 代表性组合

以下只作为常见组合参考，不代表固定模板：

- `grid` + `surface`
  适合摘要卡、重复信息卡或任意并列内容块。
- `split` + `surface`
  适合主内容区与辅助内容区并列。
- `surface` + `canvas`
  适合大面积内容承载区。
- `surface` + `stack`
  适合纵向连续的小块内容。
- `surface` + `table-area`
  适合表格或结构化明细区。

原则上只需保证原语之间可以灵活嵌套和替换，不必把页面布局穷举成固定清单。

## 请求到布局的轻量路由

以下路由只用于帮助快速起稿，不代表固定页面模板：

- 用户要“摘要概览 / KPI / overview”
  优先 `grid` + `surface`
- 用户要“主图表 + 右侧说明 / alerts / notes”
  优先 `split` + `surface`，主区内放 `canvas`，侧栏内放 `stack`
- 用户要“多个并列模块 / card gallery / module blocks”
  优先 `grid` + `surface`
- 用户要“长内容承载区 / chart / media / map / embed”
  优先 `surface` + `canvas`
- 用户要“事件流 / 状态列表 / 操作列表 / filters”
  优先 `surface` + `stack`
- 用户要“明细表 / records / rows / structured data”
  优先 `surface` + `table-area`
- 用户要“复杂 dashboard，但未指定组件”
  默认从 `grid` 摘要区 + `split` 主辅区 + `table-area` 明细区开始
- 用户明确说“不要预设内容”
  保留通用标题和占位，只输出布局骨架，不补业务组件语义

## 排版与层级

- 页面标题应明显大于 section 标题，section 标题再明显大于正文与注释。
- 一个卡片内通常只保留 1 个主标题层级，避免在卡片内部继续深层嵌套标题。
- 次要说明文字使用中灰色，避免和主数据争夺注意力。

## 响应式

- 小屏下 4 列 KPI 应降为 2 列，必要时再降为 1 列。
- 双栏布局在窄屏下应堆叠成单列，优先保证主内容在前、辅助内容在后。
- 平板宽度下应优先保留结构稳定性，不要出现列宽过窄导致的内容拥挤。
- 不要依赖悬浮、复杂动画或超宽表格来传达关键信息。
- 触控场景下按钮、切换项和可点击卡片应保留足够点击空间，避免过密。
