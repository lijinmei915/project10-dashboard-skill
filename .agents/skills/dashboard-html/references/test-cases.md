# Test Cases

> 用途：提供这套 `dashboard-html` skill 的手动测试用例，便于自测和记录问题。

## 使用方式

- 每次测试都直接触发 `$dashboard-html`。
- 先看是否输出完整独立 HTML，再看结构、样式和多端表现。
- 每个用例都记录“通过 / 不通过 / 备注”。

## Case 01: Basic Dashboard

### 输入

```txt
帮我做一个简洁的 dashboard 页面，重点统一卡片样式、区块留白和整体布局，同时适配桌面端和手机端，不要做得太重。
```

### 核验重点

- 是否输出完整 HTML 页面。
- 是否有统一外层容器和 section 分组。
- 是否沿用卡片式结构，而不是只给说明文字。
- 手机端下是否仍然能阅读。

## Case 02: KPI Overview

### 输入

```txt
帮我做一个销售概览 dashboard，首屏有 4 个 KPI 卡片，下面是趋势图和待跟进事项。页面保持简洁，重点统一卡片和留白，并适配手机端。
```

### 核验重点

- 是否有 2-4 列 KPI 卡片区。
- KPI 卡片是否统一为无边框、弱阴影、统一圆角和留白。
- 趋势图和待办是否分成独立卡片。
- 小屏下 KPI 是否会降列。

## Case 03: Status Page

### 输入

```txt
做一个简洁的系统状态页，包含页面标题、当前状态卡片、最近事件列表和说明备注，风格偏 dashboard，并适配手机端。
```

### 核验重点

- 是否保持轻量 dashboard 风格，而不是营销页风格。
- 状态、事件、备注是否分成独立卡片。
- 列表和说明层级是否清晰。
- 手机端下事件列表是否仍可扫描。

## Case 04: Table Panel

### 输入

```txt
帮我整理一个内部项目面板，上面放项目摘要卡片，下面放一个任务表格和右侧说明区，整体不要太花，并兼顾桌面和手机阅读。
```

### 核验重点

- 是否形成摘要区 + 表格区 + 说明区。
- 表格是否在独立卡片中。
- 桌面端是否形成主内容在左、辅助区在右的轻量双栏。
- 手机端下双栏是否堆叠成单栏。

## Case 05: Operations Dashboard

### 输入

```txt
帮我做一个运营 dashboard，顶部是 4 个 KPI 卡片，中间左侧放趋势图，右侧放异常提醒，底部放任务表格。要求输出完整独立 HTML，整体保持轻量，并适配桌面端、平板和手机端。
```

### 核验重点

- 是否输出完整 HTML 页面。
- 是否明显从 `assets/templates/starter.html` 的骨架演化而来。
- 是否形成 KPI 区、中部双栏、底部表格的稳定结构。
- 平板宽度下双栏是否仍可读。
- 手机端下 KPI 是否降列，双栏是否堆叠。

## Case 06: Content-Agnostic Dashboard

### 输入

```txt
用 $dashboard-html 做一个 standalone HTML dashboard。不要预设 KPI、图表、排行、待办这些固定组件，只给我一个适合后续自由替换内容的通用布局骨架，并适配桌面端、平板和手机端。
```

### 核验重点

- 是否仍然输出完整 HTML 页面。
- 是否保留通用标题与中性占位，而不是主动补业务组件。
- 是否仍有清晰的 `grid / split / table-area` 级别结构感，但不把术语显示到界面上。

## Case 07: Split vs Grid Conflict

### 输入

```txt
帮我做一个 dashboard，上半部分需要并列展示 4 个同级模块，下半部分左边是主要内容区，右边是辅助说明区。页面保持轻量并适配手机端。
```

### 核验重点

- 上半部分是否优先落成 `grid`，而不是误用 `split`。
- 下半部分是否优先落成 `split`，而不是误用等宽网格。
- 手机端下是否能正确堆叠。

## Case 08: Stack vs Table Conflict

### 输入

```txt
做一个内部 dashboard，右侧需要一组连续的说明和操作块，底部还需要一个可扫描的结构化明细区。不要做成营销页，输出完整 HTML。
```

### 核验重点

- 右侧连续块是否优先落成 `stack`。
- 底部明细区是否优先落成 `table-area`。
- 是否没有把两者混成同一种列表结构。

## Case 09: Canvas Decision

### 输入

```txt
帮我做一个 dashboard，中心区域要留一个大承载区，后续可能放图表、地图、媒体或自定义嵌入内容，其他区块保持简单辅助信息即可。
```

### 核验重点

- 中心区域是否明显是大面积承载区，而不是普通小卡片。
- 主要承载区是否位于独立 `surface` 内。
- 辅助区是否保持轻量，不抢主区层级。

## Case 10: Minimal User Instruction

### 输入

```txt
给我一个 dashboard HTML，轻一点，手机也能看，别太死。
```

### 核验重点

- 是否能按默认起稿顺序生成稳定骨架。
- 是否不会因为用户说得少就退化成杂乱布局。
- 是否仍然符合 starter 模板的基本节奏。

## Case 11: Layout Change Without Visual Drift

### 输入

```txt
用 $dashboard-html 换一版布局，做成更像后台 dashboard 的结构，但不要把内容写死。我想换布局，不是换一整套视觉规范。
```

### 核验重点

- 是否允许布局变化，但仍然保留 page header。
- 是否仍然保留标题区和辅助说明区，而不是直接丢掉头部结构。
- 卡片是否仍然保持弱阴影、浅色 surface、统一圆角和留白。
- 是否仍然沿用 `starter.html` 现有样式基线，而不是顺手重做一套新视觉。
- 若输出里定义了新的 shadow token，是否仍与 `starter.html` 的弱阴影基线一致，而不是切成另一套阴影体系。
- 是否没有因为“换布局”就自动引入更重的卡片阴影、厚边框、强品牌按钮或完全不同的组件语气。

## Case 12: Theme Accent Without Semantic Drift

### 输入

```txt
用 $dashboard-html 做一个简洁的项目状态 dashboard，使用深色模式和蓝色主题色，保留成功、提醒、错误状态的语义颜色，并适配手机端。
```

### 核验重点

- 是否使用深色 token，但仍保留原有布局、圆角、间距和弱阴影尺度。
- 是否同时包含完整的 `html[data-theme="dark"]` 覆盖与 `color-scheme: dark`，而不是只改 `data-theme`。
- 是否只将选中态、中性标签等非语义强调切换为蓝色 accent。
- 分组结构线、摘要结构线和图表主系列是否同源于深色适配后的蓝色 accent。
- 主题浅底上的蓝色文字是否达到 `4.5:1`，结构色与深色 surface 是否达到 `3:1`。
- 成功、提醒和错误状态是否仍使用各自可辨认的绿色、黄色和红色。
- 手机端下是否仍可阅读和操作。

## 通用失败信号

- 输出不是完整 HTML 页面。
- 结构看起来像一次性拼接，没有统一外层容器。
- 卡片重新出现明显描边或偏重阴影。
- 复杂场景下又回到深层嵌套、花哨装饰或营销页视觉。
- 平板或手机端出现横向滚动、内容挤压、触控区域过小。
- 单系列趋势图无依据地交替使用深浅色，造成多系列误读。

## Case 13: Header and Section Style

### 输入

```txt
用 $dashboard-html 做一个品牌报告风格的 dashboard。头部保留品牌名、页面标题和更新时间，分组标题使用编号样式；内容和布局按需求自由生成，适配手机端。
```

### 核验重点

- 是否使用 `headerStyle: brand` 与 `sectionStyle: indexed` 的视觉处理。
- 品牌、更新时间和编号是否只在用户要求时出现，不自动补业务内容。
- 页面标题、分组标题、卡片标题和辅助文字是否保持清晰层级。
- 主题样式是否没有改变内容模块和布局原语的选择。
- 手机端头部、分组标题和元信息是否自然堆叠。

## Case 14: Theme and Header Independence

### 输入

```txt
把这个 dashboard 改成深色主题，但保留当前的报告型头部、分组编号、字号、间距、布局和卡片尺寸不变。
```

### 核验重点

- 是否只替换完整颜色 token 和必要的阴影 token。
- `headerStyle` 与 `sectionStyle` 是否保持不变。
- 页面标题、分组标题、卡片标题、模块数量和结构是否保持不变。
- 是否包含完整 `html[data-theme="dark"]` 覆盖与 `color-scheme: dark`。

## Case 15: Report Routing Without Fixed Modules

### 输入

```txt
用 $dashboard-html 生成一份季度客户经营复盘报告，包含结论摘要、原因分析和客户明细，不需要 KPI 卡片。
```

### 核验重点

- 是否路由为 `pageType: report`。
- 是否按阅读顺序组织内容，而不是套用 Dashboard 的并列监控结构。
- 是否尊重“不需要 KPI 卡片”，不自动补齐固定模块。
- 是否继续使用 starter 的 token、布局原语和响应式基础。

## Case 16: Page Type and Theme Independence

### 输入

```txt
把当前企业蓝 Dashboard 改成 Report 编排，只调整阅读结构，主题色、深浅模式、字号、圆角、阴影、间距和数据都保持不变。
```

### 核验重点

- `pageType` 是否由 `dashboard` 改为 `report`。
- `visualTheme`、`mode`、`accent` 和全部非编排 token 是否保持原值。
- 用户数据、模块数量和语义状态色是否保持不变。
- 是否只调整头部密度、正文宽度、章节节奏和模块关系。

## Case 17: Layout Reordering and Sizing

### 输入

```txt
保持当前数据和视觉主题不变：把趋势分析组移到核心指标前面；核心指标组改成两列；第一张指标卡半宽，第二张整行；同组内将第三张卡片移到第一位。
```

### 核验重点

- 分组和卡片是否通过 DOM 顺序调整，而不是绝对定位。
- 卡片跨度是否使用 12 列栅格的规定档位。
- 卡片是否可以直接拖动换位，尺寸把手是否仅在悬停/聚焦时出现且不遮挡内容。
- 主题 token、数据、组件样式和语义层级是否保持不变。
- 手机端是否统一为单列且没有横向溢出。
- 最终 HTML 是否只保留布局属性，不包含设计工具控件。

## Case 18: Dashboard Card Hierarchy

### 输入

```txt
做一个全宽业务 Dashboard，不要分组小标题，每张图表和表格卡片使用自己的标题，卡片标题字号为 16px；内容按桌面宽度自适应，手机端保持单列。
```

### 核验重点

- 是否路由为 `pageType: dashboard` 并使用全宽流式内容区。
- 分组标题是否完全隐藏且不留下高度或间距。
- 每张独立卡片是否有自身标题或 KPI 标签，卡片标题是否统一为 `16px`。
- 未要求标题图标时是否保持无图标；启用后是否只改变普通卡片标题装饰。
- 页面标题、正文和 KPI 数值字号是否没有被卡片标题配置连带修改。
- 手机端是否自然堆叠且无横向溢出。

## Case 19: Dashboard Canvas and Boundary

### 输入

```txt
做一个全宽浅色 Dashboard，头部直接放在页面画布上，不要独立头部卡片和外层大圆角。页面底色与卡片都使用白色，卡片不要阴影也不要显式线框。
```

### 核验重点

- 自动头部是否使用透明紧凑样式，而不是报告式白色大头部。
- 页面是否为连续画布，最外层是否没有大圆角容器。
- 自定义页面底色恰好与卡片同色且阴影、线框都关闭时，是否自动出现极浅边线。
- 自动边线是否只解决卡片辨识度，不改变圆角、间距、字号和布局。

## Case 20: Report Shell Boundary

### 输入

```txt
把当前页面改为经营分析 Report，保留现有数据、主题、字号、卡片圆角、阴影、间距和布局，不要改成 Dashboard 风格。
```

### 核验重点

- Report 是否恢复统一整页外壳，头部和正文是否被同一个整体圆角边界包住。
- 未指定头部对齐时，Report 标题与元信息是否默认居中。
- 外壳是否保留细边界与轻阴影，且不受卡片线框开关影响。
- 自动头部是否继续使用 surface，正文是否继续使用当前页面底色。
- Dashboard 与 Report 来回切换时，是否只改变页面类型编排和外壳，不连带修改主题、字号、间距、布局或数据。
- 窄屏下外壳是否保留可见外侧留白且无横向溢出。

## Case 21: Full Agent Resource Mode

### 输入

```txt
用 $dashboard-html 根据这份销售数据生成 Dashboard。为 KPI 匹配语义图标，并用趋势图展示最近 12 周数据；默认导出静态 standalone HTML。
```

### 核验重点

- Agent/Studio 能力可用时，是否使用可信图标资源与成熟图表引擎生成结果。
- 最终 HTML 是否只内联选中的图标和图表 SVG，不包含完整 Phosphor、ECharts、搜索索引或 Agent API 地址。
- 数据值、单位、时间范围和图表标签是否与输入一致。

## Case 22: Host-Assisted Portable Mode

### 输入

```txt
在没有本项目 Studio 服务的 Agent 中，用 $dashboard-html 生成同一份销售 Dashboard；可以使用这个 Agent 已有的图标和图表能力。
```

### 核验重点

- 是否复用宿主已有能力，而不是把 Studio 当作硬依赖。
- 宿主资源是否只参与生成，默认成品是否仍可离线打开。
- 是否没有断开的本地服务地址、搜索控件或未使用的完整资源库。

## Case 23: Offline Capability Fallback

### 输入

```txt
在不能联网、没有图标库也没有图表引擎的环境中，用 $dashboard-html 生成这份经营数据的完整离线报告。
```

### 核验重点

- 可选图标是否被完整移除且不留下空白容器，文字标签是否继续表达含义。
- 图表数据是否转换为表格、排行、进度列表或 KPI 摘要，而不是空 canvas 或臆造图形。
- 标题、数据值、单位、时间范围和来源是否完整保留。
- 最终 HTML 是否仍可离线阅读并适配手机端。
